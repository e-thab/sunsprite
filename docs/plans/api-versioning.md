# API declaration codegen + version snapshots

## Context

Sunsprite's scripting API exists as several independently hand-maintained copies of the same information, and they'd already drifted apart before this work started:

- **Real runtime source** — the 6 mixins (`src/assets/api/mixins/*.ts`) each kept a private `propDescription` object of plain-English text that only their own generated doc-strings referenced; the real getters/setters themselves mostly carried no JSDoc. The 7 concrete classes (`Sprite`/`Rectangle`/`Circle`/`Label`/`Line`/`HLine`/`VLine`) each declare a bare, undocumented `*Props` type.
- **Editor-only ambient declarations** — `src/assets/api/apiLib.ts` (953 lines) hand-assembles the `apiModel`/`apiLib` strings that `CodeEditor.vue` feeds to Monaco via `addExtraLib`. It duplicates every description above with its own separate, independently hand-written copy.
- **`src/assets/api/api.d.ts`** — an orphaned stub whose own comment says apiLib's content "should be moved into here," never acted on.

Confirmed drift, not hypothetical: `mixins/Interactable.ts`'s real `onClick` JSDoc disagreed with the separate `propDescription.onClick` text for the same method. `HLine`/`VLine` both really extend `Timeable`, but apiLib.ts's hand-picked interpolation list for them omitted `${timeableApi}` — `age`/`ageMs` were silently absent from their declared surface. `apiLib.ts` declared `MouseInputAction` twice with two different underlying event lists. `apiLib.ts`'s `Camera` declaration used invalid syntax and referenced an unresolvable `Phaser.Math.Vector2`. The real `cursor` setter accepts `Cursor | string`; the hand-written declaration silently flattened this to `cursor: Cursor`.

We proved the fix mechanically in conversation before writing any of this: using the `typescript` package (already a dependency — `moduleRunner.ts` already does `import * as ts from 'typescript'`) to parse real source with `ts.createSourceFile` and pull real JSDoc via `ts.getJSDocCommentsAndTags`, reproducing exactly the hand-written doc strings then kept in the mixins. This effort formalizes and extends that proof of concept into a real tool, plus a mechanism to freeze permanent, versioned snapshots of its output.

**Original first pass was declarations/tooling only**; the editor's version dropdown has since been wired live (see "Live hot-swapping in the editor" below). Still not touched: any project-level version-selection *persistence* (nothing remembers your choice across a reload — see Future work), the runtime `api` object in `core.ts` (swapping versions changes what Monaco *thinks* is available, not what actually executes), the Core/Utilities/Camera/Vector2 sections of apiLib.ts (bug-fixed only, not derived), and docs-content versioning (facts recorded below for later, not acted on).

## Decisions locked in with the user

1. **Codegen scope**: the 6 mixins + the 7 concrete classes. Not GameObject's own members (see below); not Core/Utilities/Camera/Vector2.
2. **Known bugs found during research get fixed now**, not preserved faithfully — freezing a known bug into a permanent version snapshot is worse than fixing it before one exists.
3. **Script runtime**: `tsx` as a new devDependency. It transpiles only (esbuild) — it does not type-check. Real type-checking comes from adding `scripts/**/*` to `tsconfig.node.json`'s `include` so `vue-tsc --build` covers it too.
4. **`GameObject.ts`'s 13 boundary members are deferred entirely**, on the user's explicit call. Verified during planning: they're not merely undocumented, they're fully commented out in real source — several setters (e.g. `left`) have no logic even sketched in comment form, and `_initMixins` is marked `// WIP` right above them. Bringing them into the generated declarations would mean implementing new public API surface, not documenting existing code. Left untouched, on its own terms, for later.
5. **No `declare global` in generated or snapshotted output.** If either used `declare global { class Sprite {...} }`, every additional permanent version snapshot would collide the moment a second one exists — unlike interfaces, class declarations don't merge across ambient contexts. So the "current" generated file is a plain `.ts` module exporting **string constants** (same style as today's `positionablePropsTypeDef`), and snapshot files use real, module-scoped `export type`/`export declare class` syntax — safe to accumulate indefinitely.

    index.ts        -- generateApiDeclarations(), the one entry point both CLIs call
  generate-api.ts   -- writes src/assets/api/generated/apiDeclarations.generated.ts

`apiLib.ts` now imports the mixin `*PropsTypeDef`/`positionableApi` and all 7 concrete classes' `*PropsFields`/`*Members` constants from `./generated/apiDeclarations.generated` instead of `./mixins`. Its Core/Utilities/Camera/Vector2 sections, and the "Types" section's non-mixin half (`LibVars`, `Point`/`ArrayPoint`/`PointArg`, `Action`/`Predicate`/`Returnable`/`Printable`/`Optional`, the mouse/key event-map types), stay exactly where they were — hand-written, just bug-fixed. `CodeEditor.vue` needed zero changes: `apiLib` is still just a string, only now partly composed from an import.

The 6 mixins' `propDescription` objects and `*Api`/`*PropsTypeDef` exports are gone — deleted only after the generator was confirmed to reproduce equivalent (and bug-fixed) output. Each mixin file is now just its real `*Props` type (with JSDoc directly on the fields) and its mixin function (with JSDoc directly on the real getters/setters/methods) — one source of truth per description, not two.

**Real bugs the generator itself needed fixing for, found by actually running it (not anticipated in planning):**
- **Import-alias resolution.** `class Sprite extends GameObject` — `GameObject` is a default-imported binding, so `checker.getSymbolAtLocation()` on it returns an *alias* symbol whose `.declarations` points at the import clause, not the class. Needed `checker.getAliasedSymbol()` first. Without this fix, Sprite/Rectangle/Circle/Label's generated members silently contained only their own extra prop and nothing inherited — wrong, but not a crash, so it required actually reading the output to catch.
- **Intersection-type Props fields.** The 6 mixins' `*Props` types are plain type literals (`{ x?: number, ... }`), but every concrete class's is an intersection (`GameObjectProps & { src?: string }`). The field extractor only handled the plain case; concrete classes' own Props fields came out empty until it was taught to find the intersection's last member.
- **Untyped getters inferred as `any`.** Several real getters (`Sprite.src`, `Rectangle.color`, `Circle.color`/`radius`) have no explicit return-type annotation — TS infers it. `.getText()` on an absent type node isn't an option; needed `checker.getSignatureFromDeclaration()` + `getReturnTypeOfSignature()` as a fallback whenever there's no explicit annotation to read verbatim.
- **Double-braced snapshot output.** An early version of `snapshot-api.ts` tried to re-derive a type's body by regex-stripping the mixins' already-wrapped `declare type X = {...}` string. Fragile by construction — fixed by exposing the raw, unwrapped field-line array from the extractor instead of re-parsing pre-wrapped text.
- **Snapshot files had dangling type references.** `Cursor`, `Point`, `PointArg`, `Returnable`, `MouseInputAction`, `PointerAction`, `ScrollAction` are used throughout the generated declarations but weren't defined or imported in the snapshot file itself. This didn't surface as a `vue-tsc --build` error — `@vue/tsconfig`'s base config sets `skipLibCheck: true` project-wide, which skips deep-checking `.d.ts` file contents entirely. Verified this was a real gap (not a false alarm) by type-checking the snapshot standalone with a throwaway `skipLibCheck: false` tsconfig, which failed until the fix landed. Fixed by exporting `Cursor` from `Interactable.ts` (previously module-private) and adding `import type` lines to the snapshot for all 7 names, resolved back to their real source files. **Lesson for future snapshots**: this project's `skipLibCheck: true` means a `.d.ts` file can silently ship with broken internal references and nothing here will catch it automatically — if the generator changes what it references, re-verify standalone resolution the same way, don't trust a clean `vue-tsc --build` alone.

**One deliberate divergence from real source, kept narrow and explicit** (`sources.ts`'s `SET_TYPE_OVERRIDES`): `Line.pointA`/`pointB`'s real setter accepts `Returnable<PointArg>`, but the declared (editor-facing) type is widened to `Returnable<PointArg | number[]>`. This isn't a bug — it's a pre-existing, deliberate accommodation (see the comment that was already in apiLib.ts) for Monaco inferring a plain array literal like `[1, 2]` as `number[]` rather than the precise tuple `ArrayPoint`. A fully mechanical extraction would have silently dropped this and reintroduced the false-positive editor error it exists to prevent. If this class of override ever needs a second entry, keep it in that same table with the same kind of comment — don't let real source silently diverge from what's declared without a paper trail.

**Freshly surfaced, not previously declared anywhere**: running composition-resolution for real (rather than the old hand-picked `${gameObjectApi}`/`${viewableApi}` interpolation lists) means `HLine`/`VLine` now correctly include `age`/`ageMs` (the bug that motivated deriving composition in the first place), and `Positionable.screenX`/`screenY`, `Line.length`/`setPoints()` are declared for the first time.

## Live hot-swapping in the editor

The dropdown in `CodeEditor.vue`'s editor bar (previously `exampleVersionItems`, a hardcoded mockup) now lists real available versions and swaps Monaco's live declarations on selection.

**The design snag this required solving**: `versions/<version>/api.d.ts` (the historical snapshot built in the first pass) is a genuinely standalone module — real `export type`/`import type` syntax, resolving via imports back to real project files (`../../Point`, `../../types`, `../../mixins/Interactable`). That's exactly right for a human-readable historical record, but wrong for Monaco: the editor's TS environment is an isolated sandbox fed only through `addExtraLib`/`createModel` with fabricated virtual URIs — it has no access to real project files, so those imports can't resolve there, and its content isn't ambient-global anyway (it has real exports, so under the editor's `moduleDetection: "force"` setting it would be scoped to itself rather than globally visible to user scripts).

**Resolution — two artifacts per snapshot now, not one**: `scripts/snapshot-api.ts` writes `api.d.ts` exactly as before (unchanged, still the standalone historical record) and now *also* writes `versions/<version>/generated.ts`, mirroring the shape of `generated/apiDeclarations.generated.ts` — bare, ambient-ready string constants, factored out into a shared `scripts/api-codegen/render.ts` (`renderGeneratedModule`) so both CLIs produce it identically. `apiLib.ts` itself changed from a static `const` into an exported `buildApiLib(v: VersionedApiConstants): string` function — Core/Utilities/Camera/Types-preamble stay fixed inside it, only the mixin/class-derived pieces are parameterized — with `apiLib` now just `buildApiLib({...the live generated imports...})`, so the default/current behavior is byte-identical to before.

`src/assets/api/versions/index.ts` is the new browser-side piece: `import.meta.glob('./*/generated.ts')` (lazy — versions accumulate, most won't be selected in a given session) enumerates and loads them; `loadVersionedApiLib(version)` calls `buildApiLib()` on a loaded historical version's constants, producing the exact same kind of ready-to-register string `apiLib` is. `CodeEditor.vue`'s `selectApiVersion()` disposes the currently-registered extra-lib (`addExtraLib` layers rather than replacing in place — the previous registration has to be disposed before a new one at the same URI takes clean effect) and registers the new one, then nudges the active model to re-validate via the same `refreshDiagnostics` mechanism already used after every file-switch remount (Monaco doesn't automatically repaint already-open squiggles just because the ambient lib changed underneath them).

**Not yet verified live**: this was checked as far as static tooling can — `vue-tsc --build` clean, `buildApiLib()`'s output re-confirmed byte-sane after the const-to-function refactor. `import.meta.glob` is Vite-only, so the glob resolution, the dropdown's real rendering, and the actual live swap in a running Monaco instance haven't been exercised yet — need the dev server for that, not done unprompted per this project's own working norms.

## Runtime source versioning

The gap the two sections above both flagged — "selecting a version only changes what Monaco *thinks* is available, not what actually executes" — is now closed too. `pnpm run snapshot-api -- <version>` now also copies the real, runnable source behind the API into `versions/<version>/src/`, and the sandboxed game actually executes against a historical version's real classes when one is selected.

**Why copying, not parametrizing, an existing engine**: research before implementing established that `core.ts` and the API classes aren't layered — they're one strongly-connected component. 14+ files (`Camera.ts`, `Random.ts`, `Sprite.ts`, all 6 mixins, etc.) have live circular imports back into `core.ts` (`camera`, `scene`, `screen`, `mouse`, `clock`, `allPositionables`, `forever`, and more). There's no clean seam to thread a version parameter through instead — confirmed, not assumed, by grepping every `from "./core"` edge in `src/assets/api/`.

**Copy-set (28 files)**: all of `src/assets/api/*.ts` and `mixins/*.ts` except `moduleRunner.ts`/`scriptResolution.ts` (generic script-compilation engine, version-agnostic — operates on an opaque `api: Record<string, unknown>` with no idea what's in it), `examples.ts`/`gameAssets.ts` (zero imports, host-only), `api.d.ts`/`apiLib.ts` (the declaration system itself), and `src/assets/api/output.ts` (the *host-side* DOM output renderer — confirmed to be a different file from `src/sandbox/output.ts`, the one `core.ts` actually imports) — plus `src/sandbox/watch.ts` and `src/sandbox/output.ts`, confirmed in scope with the user despite sitting outside `src/assets/api/`, since `core.ts` can't run without them. Mirrored under `versions/<version>/src/` at each file's real `src/`-relative path, so imports between two copied files resolve unchanged by construction — the rewriter (`scripts/api-codegen/runtimeCopy.ts`) only ever touches imports crossing the copy-set boundary (pointing them back at the live, unversioned original via `path.relative()`).

**A real bug caught by building this, not anticipated in planning**: `src/sandbox/main.ts` imports `collectWatchSnapshot` from `./watch` *independently* of `core.ts`. If `main.ts` kept statically importing the live `watch.ts` while a versioned `core.ts` used its own copied one, a script's `watch()` calls would populate a private `cards` map the status-report loop never sees — the Watch panel would silently show nothing for any non-latest version. Fixed by loading `core` and `watch` together, as a pair, from the same version (`versions/runtime.ts`'s `loadVersionedRuntime()`).

**A second bug, caught only by actually running the rewriter, not by reasoning about it**: the first implementation attempt rewrote *zero* `@/`-aliased imports — `core.ts`'s copy still said `from '@/sandbox/watch'` verbatim. Root cause: `ts.resolveModuleName` always returns forward-slash paths regardless of platform; `path.join`/`path.resolve` return backslash paths on Windows; the copy-set membership check (`Set.has()`) silently never matched, so *every* resolved import looked like it pointed outside the copy set. Fixed by normalizing both sides to forward slashes before comparing. Worth remembering for any future path-comparison code in this toolchain — this class of bug produces no error, just silently wrong output, which is exactly why the automated standalone verification (next paragraph) exists rather than trusting the rewriter by eye.

**Verification is two-pronged, not one check trying to do both jobs**: an initial version tried a single alias-free `ts.createProgram` check and got noisy false positives — `core.ts` correctly pointing back at the live, never-copied `moduleRunner.ts` caused TypeScript to transitively pull in `moduleRunner.ts`'s *own* untouched `@/sandbox/protocol` import, which an alias-free config can't resolve even though that file was never supposed to be touched. Split into (1) a text-level check that no copy-set file still contains an unrewritten `@/`-style specifier (proves rewriter *completeness*), and (2) a real `ts.createProgram` check using this project's actual alias config with `skipLibCheck: false` (proves rewriter *correctness* — unlike the declaration snapshots, these are real `.ts` files, not subject to `skipLibCheck`'s blind spot). Both run automatically inside `snapshot-api.ts`, every time, not as a manual one-off.

**How a version actually takes effect**: `CodeEditor.vue`'s dropdown now writes `apiVersionStore` (new Pinia store, session-local, modeled on `useFullscreenStore` — reset on `EditorView.vue` unmount the same way `PlayView.vue` already resets fullscreen) instead of a local ref. `hostBridge.ts` reads it directly to build the sandbox iframe's URL (`?apiVersion=<v>`) and, inside the existing `runUserCode()` — the one choke-point every run path already goes through (per-script Run, Restart, FileTree "Run script", PlayView Restart) — forces a real iframe reload (`frame.src = sandboxUrl()`) whenever the selection doesn't match what's currently loaded. **A version change never hot-patches a running game** — confirmed nothing in this app reloaded the iframe before this work (Restart only ever `postMessage`'d into the same live document), so this is new, deliberate behavior: Phaser scenes/GameObjects already built from old classes can't sanely swap which class backs them mid-execution, so a version change takes effect on the next fresh run, full stop. `main.ts` reads the version off its own `location.search` at module top (top-level `await`, fine in a `type="module"` script) before `setup()` runs — a `HostMessage` field would arrive too late for this and was deliberately not added for that reason.

## Project-level persistence

Closes the gap the last section's own "Future work" bullet named: a project now remembers which permanent version it's pinned to, instead of every session silently starting at "Latest."

**The versioning policy, as the user specified it**: versions are X.Y.Z. X is a breaking-change boundary — never crossed silently, so any upgrade that keeps X fixed (1.2.5 → 1.5.0, 1.0.5 → 1.9.9) is safe by construction. Only X.Y is ever user-visible or selectable; Z is bugfix-tier and doesn't get its own separately-selectable entry — 1.2.0 and 1.2.8 both just read as "1.2," and once a newer Z exists for a given X.Y, an older Z in that same tier is no longer reachable.

**A discrepancy surfaced before writing any code, not after**: that policy was described in three-part X.Y.Z terms, but the two real snapshots already on disk (built earlier in this same effort) are named `0.0` and `1.0` — two-part. Re-reading the policy against that reality: "the minor tier doesn't need its own snapshot" reads most consistently as *bugfix-tier changes re-cut the same X.Y folder in place* rather than accumulating parallel `X.Y.Z` folders that then need pruning/grouping logic — which is exactly what already happened, informally, earlier this session (`0.0.1`/`1.0.0`, as they were called in conversation, were re-cut in place at least twice to carry a source fix forward, never left as separate selectable copies). Under that reading, the on-disk folder name *is* the X.Y tier, full stop — there is no persisted Z anywhere, and no grouping/"latest Z within this X.Y" resolution layer was needed. `listApiVersions()`, `loadVersionedApiLib()`, and `loadVersionedRuntime()` (all from the prior two sections) already operate in exactly the right unit and needed zero changes for this pass. Confirmed with the user only on the two questions that genuinely weren't derivable from the description — when a project's version gets set (at creation, from whatever tier is newest then, fixed until explicitly changed) and whether picking a new one saves immediately (yes, no separate save step) — rather than on this folder-naming question, which the existing repo state answered on its own.

**Schema**: `public.projects.api_version` (migration `20260829120000_add_project_api_version.sql`) — `text not null`, backfilled to `'1.0'` (the tier that was actually newest at migration time — an application-level fact, not derivable from the row the way slug's backfill was, so it's a plain literal rather than an expression), with a format check (`^[0-9]+\.[0-9]+$`) mirroring `projects_slug_format`'s existing shape. New projects get `latestApiVersion()` (`versions/index.ts` — just `listApiVersions()[0]`, falling back to `'latest'` only if literally nothing has ever been cut) at creation time in `projectStore.ts`'s `createProject`, and never move afterward except through the dropdown.

**A generated file needed a manual edit, not a migration-only change**: `src/assets/utils/database.types.ts` is Supabase-CLI-generated but has no regeneration script in this repo (no local/linked Supabase instance to run it against from here) — it's checked in and hand-maintained when it drifts. Adding the migration alone left every `.select()`/`.insert()` call site failing to type-check (`SelectQueryError<"column 'api_version' does not exist...">`) until `projects`' `Row`/`Insert`/`Update` shapes were edited by hand to match, mirroring exactly how `is_public`/`slug` already appear there. Worth remembering for the next column: the migration and this file are two separate edits, and only one of them is enforced by `vue-tsc`.

**Wiring, following the same shape `is_public`/`slug` already established**: `ProjectRecord` gained `apiVersion`; both hardcoded `.select()` column lists in `projectStore.ts` (`fetchProjects`, `createProject`) and both row-mapping blocks gained `api_version`/`apiVersion`; `setApiVersion(id, version)` mirrors `setPublic` exactly. `ProjectEditorView.vue` and `PlayView.vue` — the two places that already do their own raw `.select()` by slug rather than going through the store's list (one owner-scoped, one guest-accessible) — each select `api_version` too and write it straight into `apiVersionStore.selectedVersion` the moment the row resolves, before their child (`EditorView`/`GameFrame`) ever mounts. `CodeEditor.vue`'s `selectApiVersion()` gained a write-through call to `setApiVersion()` right after it updates the store — fire-and-forget with a `console.error` on failure, matching this file's existing (lack of) error-surface convention rather than inventing a new one, since nothing here has a UI slot for it.

**`'latest' is deliberately excluded from persistence, and no longer a dropdown entry at all** *(the dropdown half of this was superseded — see "The `dev` entry" below; the persistence half still holds, under the new name)*: the live, unversioned, currently-in-development source (`apiLib`/`loadLatestRuntime()`) is still what the `'latest'` sentinel means internally (`apiVersionStore`'s default, guest sandbox mode, `main.ts`'s fallback on an unresolvable version), but it's not something a project can be pinned to or a user can pick from `CodeEditor.vue`'s dropdown — that list is built straight from `listApiVersions()` now, no separate "Latest" row spliced in. Since `listApiVersions()` already sorts newest-first, index 0 *is* the most up-to-date real version; the dropdown just appends "(Latest)" to that one row's label as a decoration, and selecting it pins the project to that concrete version exactly like any other row — it does not start tracking newer versions cut afterward. `setApiVersion`'s write-through is still gated on `version !== 'latest'`, which now only matters for the sentinel's remaining internal callers, not anything reachable from this dropdown. `apiVersionStore.ts`'s own comment was rewritten to stop claiming "no project/profile column" now that one exists.

**`PlayView.vue`'s gap, flagged in this doc's own prior "Future work" and now closed**: it previously had zero version-awareness and always played at "latest," meaning a public project's live page could have silently broken the moment "latest" crossed a breaking major-version boundary — exactly the failure mode the whole X.Y policy exists to prevent for the *editor*, just left open on the play side. It now hydrates `apiVersionStore` from the same `api_version` column before its first `runUserCode()` call, and resets the store on unmount (it never did before this pass — nothing needed resetting when nothing was ever set).

**Not yet verified live**: migration not yet applied to any real database from this session (schema changes against a shared Postgres instance aren't something to run unprompted) — `pnpm run type-check` is clean against the hand-edited `database.types.ts`, but the actual round-trip (create a project, confirm it's pinned to "1.0," switch versions, reload, confirm it stuck; load a public project as a guest and confirm it plays at its pinned version) needs the migration applied first, then the dev server, then explicit go-ahead per this project's established norm.

## The `dev` entry (later pass)

**What changed**: the internal `'latest'` sentinel was renamed to `'dev'` (`src/assets/api/versions/constants.ts`, a new dependency-free module) and promoted to a real, selectable row in `CodeEditor.vue`'s dropdown. It means exactly what the sentinel always meant — the live source in the working tree, declarations *and* runnable code, not a frozen copy — the difference is that it's now reachable from the UI instead of being a state you could only start in and never return to.

**Why a rename rather than a second id alongside `'latest'`**: adding `dev` as a distinct entry would have left two ids with identical behavior and no way to tell them apart in the UI — the badge would read "Latest" for the sentinel (the state a guest sandbox boots into) while a separate `dev` row did the same thing, and neither would ever show a checkmark against the other. The rename also disambiguates a real collision in this doc's own vocabulary: "Latest" as a *dropdown label* means the newest cut snapshot (`latestApiVersion()`, the tier new projects are pinned to), which is a different thing from the live source and always was. Nothing persisted `'latest'` anywhere — never written to `projects.api_version` (the format check rejects it), never in localStorage — so the rename had no migration surface.

**Where the id lives, and why it isn't in `versions/index.ts`**: both sides of the host/sandbox split need to agree on it, and neither may import the other's module — `index.ts` globs every snapshot's Monaco declarations (host-only), `runtime.ts` globs their runnable source (sandbox-only), and that separation is exactly what keeps versioned `core.ts` copies out of the host bundle. `constants.ts` has no imports at all, so `hostBridge.ts` and `sandbox/main.ts` can both take it for free.

**Resolution is centralized rather than branched at each call site**: `loadVersionedApiLib('dev')` returns the live `apiLib`, and `loadVersionedRuntime('dev')` delegates to `loadDevRuntime()` (renamed from `loadLatestRuntime()`). `CodeEditor.vue` and `sandbox/main.ts` each dropped their own `=== 'latest'` branch as a result — one function per side now maps any version id to what it means.

**`listApiVersions()` deliberately still excludes it**: `latestApiVersion()` reads element 0 of that list to decide the tier every *new project* is created against, and the sort is descending — `'dev'` sorts ahead of any numeric label, so folding it in would silently pin every new project to a moving target, and to a value `projects_api_version_format` rejects outright. The dropdown concatenates the two itself, as two visually separated groups (live vs. permanent).

**`dev` is reserved, not a folder**: `scripts/snapshot-api.ts` refuses `pnpm run snapshot-api dev` outright. A `versions/dev/` directory would be picked up by both globs and shadow the live entry with a frozen copy of the very thing it exists to bypass — the editor would go on offering a `dev` row that quietly stopped tracking anything. Verified by running it: exits 1, writes nothing.

**Dev builds only**: the dropdown row is gated on `DEV_VERSION_AVAILABLE` (`versions/index.ts`), which is just `import.meta.env.DEV` — true under `vite dev`, statically `false` in anything `vite build` produces, so the row is dead-code eliminated out of production rather than hidden at runtime. Chosen over the `location.hostname === 'localhost'` test that prompted this: what matters isn't where the page is served from but whether the API is still live, and a production bundle has it frozen in at build time — a 'dev' row under `vite preview` would be an unnamed snapshot wearing the dev label. The flag also survives `vite dev --host` (dev server reached at a LAN address, e.g. from a phone), which a hostname test would wrongly reject. It lives in `index.ts` rather than beside `DEV_VERSION` in `constants.ts` because `snapshot-api.ts` imports that module under tsx, where `import.meta.env` doesn't exist at all.

**The default follows the same gate** (decided with the user after the above landed): `apiVersionStore`'s `DEFAULT_VERSION` is `DEV_VERSION_AVAILABLE ? DEV_VERSION : latestApiVersion()`. Production no longer starts the guest sandbox on a version its own dropdown can't show as selected or switch back to — it starts on the newest cut snapshot, i.e. exactly what a freshly created project gets from `createProject`, so the two behave identically out of the box. The tradeoff accepted: a production guest sandbox runs the newest *snapshot* rather than the deployed live API, so an API change that's deployed but not yet snapshotted won't reach guests until a version is cut for it. Dev builds still start on `dev` — that entry exists so a working-tree change is runnable without ceremony, and since this ref is session-local, a snapshot default there would mean re-picking `dev` from the dropdown after every reload.

**A dev build ignores a project's pin too**: `apiVersionStore.hydrateFromProject(savedVersion)` replaced the direct `selectedVersion = data.api_version` assignment in both `ProjectEditorView.vue` and `PlayView.vue`, and applies the same `DEV_VERSION_AVAILABLE` override — production runs a project on exactly the tier it's pinned to, a dev server runs it on the working tree. Without this, the dev entry only ever applied to the guest sandbox: opening any real project (the normal way to test an API change against actual content) would have snapped straight back to a frozen snapshot, and got there again on every reload, since the ref is session-local. Nothing is written back — the pin is only persisted by an explicit dropdown selection — so running a project on dev locally can't quietly re-pin it. Its real tier stays visible in `ProjectsView`'s list, though *not* in the editor while dev is active, which is the one cost of this.

**Known limitation, unchanged from the sentinel's own behavior**: selecting `dev` in a real project is session-local. `setApiVersion`'s write-through is skipped for it (there's nothing meaningful to pin to, and the column's format constraint only accepts `X.Y` anyway), so reopening the project comes back up on whatever snapshot it's actually pinned to. Persisting a project *on* dev would need the check constraint relaxed — a migration, not attempted here.

**Not yet verified live**: type-check clean; the reserved-label guard exercised for real. The dropdown's rendering as two groups, the checkmark landing on `dev` in the guest sandbox, and the actual live swap (Monaco's declarations and the sandbox reload) still need the dev server and explicit go-ahead, per this project's norm.

## Docs content versioning

Closes the last remaining gap named at the very top of this doc: `content/api/**` — the API reference pages — now gets frozen per version too, the same way the runtime already does, and both `DocsPanel.vue` (in-editor) and `DocsView.vue` (the standalone `/docs` route) render whichever version's copy is active instead of always the live tree.

**Scope, decided with the user before writing code**: only `content/api/**` (69 pages) is ever frozen. `content/concepts/`, `content/tutorials/`, `content/ui/` (11 pages) stay one evergreen set, shared by every version — they don't describe versioned API behavior, so freezing them would just mean an edited tutorial stays stale under every older version for no reason. Direct consequence: a historical version's docs tree is a *merge* — that version's own frozen `api` category node, spliced into the live tree in place of its own, with `concepts`/`tutorials`/`ui` always coming from the live tree regardless of which version is showing.

**A real complication the runtime-versioning precedent didn't have to deal with**: doc pages aren't all static prose. `content/api/colors.vue` and the four `content/api/functions/random/*.vue` pages import real API modules (`@/assets/api/Random`, `@/assets/api/Colors`, `@/assets/api/utility`) and execute them inline (`Random.color()`, iterating `WebColors`) to render live examples — in the *host* Vue app, not the sandbox. Confirmed by actually reading the files, not assumed from this doc's own earlier (now-corrected) claim that docs content had "zero programmatic imports." A frozen copy of these pages needs the same import-rewriting the runtime copier does, or a historical version's "live" example would keep calling the *current* `Random.color()` regardless of which version's docs it's supposedly showing.

**The rewriter reuses `runtimeCopy.ts`'s resolution helpers, not a second implementation of them**: `scripts/api-codegen/vueCopy.ts` (new) parses each `.vue` file with `parse()` from `vue/compiler-sfc` — a subpath export of the `vue` package already a direct dependency, confirmed working with zero new dependencies despite pnpm's strict `node_modules` layout making the bare `@vue/compiler-sfc` specifier itself unreachable. Only the `<script>`/`<script setup>` block(s) are extracted, parsed as TS, and rewritten (same specifier-resolution logic `runtimeCopy.ts` already has, exported for reuse: `resolveSpecifier`/`mirroredPath`/`toSpecifier`/`normalizeSlashes`/`RESOLUTION_OPTIONS`) — `<template>`/`<style>` are copied untouched. Verification is deliberately real temp `.ts` files written next to the copy and cleaned up in a `finally`, not a synthetic in-memory `ts.CompilerHost` — an earlier draft of `verifyVueStandalone` used a custom host with an overridden `getSourceFile`, and was replaced before landing: real files are less fragile and match `verifyStandalone`'s own existing shape (`ts.createProgram` over real paths) instead of introducing a second, riskier technique for the same job.

**The copy-set union is what makes a live-example page resolve to *its own version*, not the original**: a doc page's import is checked against `runtimeCopySet() ∪ docsCopySet()`, not `docsCopySet()` alone. Verified directly, not just reasoned about — cut a throwaway snapshot and read the copied `colors.vue`: its `import { WebColors } from '@/assets/api/Colors'` came out as `from "../../../api/Colors"`, three directories up from the copy's own mirrored location (`versions/<v>/src/assets/docs/content/api/colors.vue`) to `versions/<v>/src/assets/api/Colors.ts` — that version's own already-copied file, not the live original. `docsCopySet()` itself (`sources.ts`) is a dynamic recursive walk of `content/api/**/*.vue`, not a hand-enumerated list — doc pages are numerous and open-ended, and `docsContent.ts` already treats `content/**` as glob-discovered with "no manifest to keep in sync"; the copy-set inventory shouldn't be the one place that breaks that property.

**One command, unchanged**: `scripts/snapshot-api.ts` gained one more step in `main()`, inside the same `existsSync` permanence guard as the runtime copy — a version's declarations, runtime, and docs move together or the whole point of freezing them is undermined.

**Host-side tree building went from one fixed computation to a reusable factory** — the same const-to-function shape `apiLib.ts` was already refactored into earlier in this effort (`buildApiLib(v)` + `apiLib = buildApiLib({...live imports})`), applied here to `docsContent.ts` (`buildDocsTree(pageModules, pageSources)`, keys pre-stripped of their glob prefix by the caller so the function itself doesn't need to know whether it's building the live tree or a historical one) and `docsIndex.ts` (`buildDocsIndex(tree)`, returning `{nodesByPath, searchEntries, ancestorsOf}` — cheap, one O(n) walk). `docsSearch.ts`'s `searchDocs(query, entries)` takes entries explicitly now instead of reading a fixed module-level singleton.

**New `src/assets/docs/docsVersions.ts`** is the host-side counterpart to `src/assets/api/versions/runtime.ts` (sandbox-side) — same idea (lazy `import.meta.glob`, keeps every non-active version's pages out of the initial bundle), different side of the app, since docs render in the host, not the sandbox. Its glob (`'../api/versions/*/src/assets/docs/content/api/**/*.vue'`) groups matches by version via regex, re-prefixes each relative key with `api/` so a versioned page's node `path` matches its live counterpart exactly (`api/colors`, not just `colors`) — required for `DocRelated`/`DocMixins`' path-string cross-links to keep resolving inside a historical version's own subtree. `loadVersionedDocsData(version)` is memoized per version; `useDocsData(version)` wraps it reactively (seeded synchronously to the live tree so there's no flash of empty content on mount, then a `watch(version, ..., {immediate: true})` takes over) for `DocsPanel.vue`/`DocsView.vue` to `provide()` directly.

**A new injection key, deliberately separate from `docsNavigationKey`**: `docsDataKey` (`docsData.ts`) carries `Ref<{tree, nodesByPath, searchEntries, ancestorsOf}>` for whichever version is active. Kept apart from navigation state (current path, expand/collapse) on purpose — which category is expanded is orthogonal to which version's data backs it, so a version switch shouldn't reset what the user expanded, and expanding a category shouldn't care which version it's browsing. `DocsTree.vue`, `DocsBreadcrumb.vue`, and `useDocRefs.ts` switched from importing `docsIndex.ts`'s old module-level singletons to `inject(docsDataKey)`.

**Two more call sites needed fixing that weren't in the original file list**, found only by actually running `pnpm run type-check` after the `searchDocs` signature changed, not anticipated in planning: `DocsSearchModal.vue` (a globally-mounted command palette, not nested under either `DocsPanel.vue` or `DocsView.vue`'s provide tree) and `DocsSearchResultsView.vue` (`/docs/search`, a *sibling* route to `DocsView.vue`'s `/docs/:pathMatch`, not nested inside it). Neither has a version context of its own to follow, so both were left searching the live/current `docsIndex.ts` singleton — deliberately, not as an oversight; giving either one its own selector would have been a real scope increase beyond what was approved.

**`DocsPanel.vue` follows `apiVersionStore.selectedVersion`** (the same version the project and sandbox are already pinned to) **with no selector of its own** — there's never a state where the docs panel and the running code disagree about which version they're showing. **`DocsView.vue` gets its own independent selector** (a local `ref`, session-only, no persistence — the user's explicit call, since it's reached outside any project) — its dropdown reuses the exact item-building logic `CodeEditor.vue`'s own dropdown uses, pulled out into `apiVersionDropdownItems(selected, onSelect)` (`versions/index.ts`) so the two look and behave identically rather than maintaining two copies of the same grouping ("(Latest)" label, `dev`-row gating) by hand. `CodeEditor.vue` itself now just calls that shared function.

**Verified beyond type-checking**: a throwaway snapshot's copied `colors.vue` was read directly to confirm the import rewrite (see above), and `npx vite build` (a real production build, not the browser — exercises `import.meta.glob` for real, which `vue-tsc` doesn't) completed clean with the throwaway version present, producing separate `core-*.js`/`generated-*.js` chunks per version as expected. **Not yet verified live**: the actual in-browser behavior (DocsPanel following a version switch, DocsView's own dropdown, search/breadcrumbs/tree working against a historical version's merged tree) needs the dev server and explicit go-ahead, per this project's established norm.

## What this pass does and does not cover

**Covers**: JSDoc-derived declaration generation for the 6 mixins and 7 concrete classes; a `versions/<label>/` snapshot mechanism (`api.d.ts` + `generated.ts` + real runnable `src/`, now including `content/api/**`'s doc pages) triggered by one npm script; the bug fixes listed above; live hot-swapping of Monaco's declarations, the sandboxed game's actual runtime behavior, *and* the in-editor/standalone docs content, all via a version selector; project-level persistence of the selected X.Y tier, including the played (`PlayView.vue`), not just edited, side.
